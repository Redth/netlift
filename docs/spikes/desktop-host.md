# Native macOS/CoreCLR round-trip spike

**Status:** verified on this development Mac on 2026-09-25. This is a
desktop hosting control experiment, **not** an iOS/Android mobile-host
proof or a shipping NetLift ABI.

The native C++ executable in `spikes/desktop-host/host.cpp` uses `nethost`
to locate `hostfxr`, calls `hostfxr_initialize_for_runtime_config`, obtains
`hdt_load_assembly_and_get_function_pointer`, and loads a generated
`[UnmanagedCallersOnly]` C-callable method in the .NET 11 class library.
The managed method starts asynchronous `OrdersService.PlaceAsync` work,
calls a native confirmation callback from its worker, then calls a native
completion callback. The native host waits with a bounded timeout and
checks the result. Neither side lets an exception unwind across C; the
managed worker prints an exception and returns failure code `-2`.

Run from the workspace root:

```sh
bash spikes/desktop-host/run.sh
```

Observed with .NET SDK `11.0.100-rc.1.26425.128` on macOS arm64:
build succeeded with 0 warnings/0 errors; the executable printed
`Native macOS host -> CoreCLR -> native callback -> CoreCLR -> native completion passed.`
The script locates the installed .NET 11 RC 1 host pack and pins the
framework-dependent runtime config generated by the managed project.

This validates the desktop `hostfxr` call path and a round trip through
native/managed/native async callbacks. The native callbacks use process-
lifetime static functions and the host waits for completion, so it does
**not** validate retention of an escaping Swift/Kotlin closure, CoreCLR
mobile startup/packaging, JNI reference ownership, app signing, or ABI
version negotiation. General
[native-hosting documentation](https://learn.microsoft.com/dotnet/core/tutorials/netcore-hosting)
explicitly limits its `hostfxr` recipe to framework-dependent deployments;
it cannot be used as evidence that a self-contained signed iOS/Android
native-owned app works.
