# Minimal native Orders screens (implemented v3 route)

These are small **UI slices**, not standalone apps or SDK templates. Read the
[SwiftUI screen](../../spikes/apple/NativeSwiftHost/OrdersMinimalScreen.swift)
and [Compose screen](../../spikes/android/NetLift.AndroidRuntime/sample/src/main/java/com/netlift/sample/OrdersMinimalScreen.kt)
side by side: each receives an already initialized **generated client**,
calls `placeAsync` with a generated `OrderDraft`, renders the typed
`OrderReceipt`, and can cancel an in-flight call. There are no C handles,
JNI calls, serialized DTOs or CoreCLR pointers in either screen.

```swift
let receipt = try await client.placeAsync(
    draft: OrderDraft(sku: sku, quantity: Int32(quantity)))
```

```kotlin
val receipt = client.placeAsync(OrderDraft(sku, parsedQuantity))
```

| Layer | Apple | Android |
| --- | --- | --- |
| Developer-authored business code | [`Orders.Business`](../Orders.Business/OrdersService.cs): `PlaceAsync` awaits `IConfirmation.ConfirmAsync` before returning a receipt | Same plain managed library |
| Opted-in contract | The prototype's [annotated contract](../../spikes/android/NetLift.AndroidRuntime/sample/managed-orders/OrdersV4Contract.cs) selects DTOs, the managed `PlaceAsync` route and the native `ConfirmAsync` route | Same schema, projected for Kotlin |
| Generated native call | `NetLiftAsyncClient_2.placeAsync(draft:)` and `OrderDraft` from [`Generated/NetLift.swift`](../../spikes/apple/NativeSwiftHost/Generated/NetLift.swift) | `OrdersClient.placeAsync(OrderDraft(...))` from the projected [`NetLift.kt`](../../spikes/apple/NativeSwiftHost/Generated/NetLift.kt) (regenerated by the Android build) |
| App-owned integration | [`NativeHostState`](../../spikes/apple/NativeSwiftHost/NativeHostView.swift) starts CoreCLR, supplies the generated client's confirmation handler and closes it | [`MainActivity`](../../spikes/android/NetLift.AndroidRuntime/sample/src/main/java/com/netlift/sample/MainActivity.kt) creates the client with an `AndroidOrdersAbi`, suspending confirmation dialog handler and lifecycle scope; it closes the client on teardown |
| Minimal UI | `OrdersMinimalScreen(client:)` | `OrdersMinimalScreen(client)` |

The Compose screen compiles in the existing Android sample module; the
SwiftUI screen is listed in the XcodeGen target and typechecks with its
actual generated facade against the iOS Simulator SDK. Neither is
**installed as the default entry screen**. The existing hosts remain the
executable simulator/emulator proof with their negative and lifecycle
controls. To display a minimal screen in a proof app, pass its
already-started client from the app-owned host state; do not create a
second bridge or registration in a view/composable. The host owns startup,
native-origin confirmation presentation, cancellation/revoke/drain and
close; view disappearance only cancels the view's current operation.

To check just these native surfaces from the repository root:

```sh
xcrun swiftc -typecheck -target arm64-apple-ios15.0-simulator \
  -sdk "$(xcrun --sdk iphonesimulator --show-sdk-path)" -swift-version 5 \
  -I spikes/apple/NativeSwiftHost/Generated \
  -import-objc-header spikes/apple/NativeSwiftHost/CoreCLRHost.h \
  spikes/apple/NativeSwiftHost/Generated/NetLift.swift \
  spikes/apple/NativeSwiftHost/OrdersMinimalScreen.swift
MSBuildEnableWorkloadResolver=false \
  ./spikes/android/NetLift.Compose/gradlew \
  -p spikes/android/NetLift.AndroidRuntime \
  :sample:compileDebugKotlin --offline --no-daemon --quiet
```

The second command uses an existing wrapper distribution and cached
Android dependencies; remove `--offline` if dependencies are not already
available. The resolver override only bypasses an inconsistent local
.NET RC workload-set installation for these plain managed projects.
Building the entire iOS host also invokes runtime-staging scripts and
requires matching .NET runtime packs; a Swift typecheck is not an
end-to-end simulator run.

This is the **older v3 `Orders.Business` contract**, not the newer
[`Orders.AsyncBusiness`](../Orders.AsyncBusiness/README.md)
`SubmitAsync`/`ConfirmAsync` profile. The newer profile's mobile proof
apps still hand-wire the V2 host and expose *generated request/result
codecs rather than a typed Swift/Kotlin `SubmitAsync` service client*.
The Swift v3 confirmation callback is synchronous at the generated
boundary and its proof host uses a blocking off-main gate to present
SwiftUI; do not copy that adapter into an app as an async-callback
recommendation. The Android v3 generated client supports a suspending
confirmation handler. An idiomatic, small end-to-end **v5** sample
needs generated typed async clients and an async Swift confirmation owner
on the actual v5 host, followed by tested native package/loader setup.
Neither these UI slices nor the proof apps satisfy product `ACTIVE`,
device, signed distribution or one-step consumer-build gates.
